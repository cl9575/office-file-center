# 系统架构与维护说明

本文面向后续开发和维护人员。

## 1. 设计目标

- 十几人、一台 Windows 主机、局域网浏览器访问。
- 部署简单，不依赖 Docker、外部数据库或客户端软件。
- 文件可追溯、可恢复，误删可找回。
- 单进程、单主机，结构清晰，便于维护和扩展。
- 数据安全和备份可验证，不把“有历史版本”误当成“有备份”。

明确的非目标：本地自动同步、SVN 工作流、在线协同编辑、全文检索、分布式部署、复杂部门权限。

## 2. 组件

```text
web/ (React + Ant Design + Vite)
        │ 构建到 internal/webui/dist
        ▼
internal/webui (go:embed)
        │
cmd/server ── internal/api ── internal/auth
        │            ├────── internal/files ── internal/storage
        │            ├────── internal/audit
        │            ├────── internal/settings
        │            └────── internal/backup
        ├── internal/db (SQLite WAL + 迁移)
        ├── internal/certsetup (本地根证书与服务器证书)
        └── internal/service (Windows 服务)
```

程序以 Windows 服务方式运行，服务账号为 `NT AUTHORITY\LocalService`。数据目录与程序目录分离，升级程序不覆盖数据。

## 3. 数据布局

```text
<data>/
├── meta.db           SQLite 数据库，WAL 模式
├── objects/ab/<id>   不可变文件内容，按 ID 前两位分目录
├── tmp/              上传临时文件
├── certs/            自动生成的根证书与服务器证书
└── logs/             服务日志
```

对象路径只由服务端生成的随机 ID 决定，不使用用户提供的路径。文件名只用于显示和下载响应头，避免路径穿越和大小写覆盖。

## 4. 数据库模型

| 表 | 作用 |
|---|---|
| `users` | 账号、Argon2id 密码摘要、角色、主机账号标识、强制改密、停用、软删除标记 |
| `sessions` | 会话令牌的 SHA-256、过期时间 |
| `nodes` | 文件/文件夹节点、父目录、当前版本、修订号、软删除批次 |
| `versions` | 版本号、对象 ID、大小、SHA-256、上传人、说明 |
| `objects` | 不可变内容对象目录 |
| `audit` | 操作日志快照（操作人、对象名称/路径、结果、IP） |
| `settings` | 平台名称、大小限制、保留空间、备份策略 |
| `upload_tasks` | 上传幂等记录和中断恢复 |
| `backup_runs` | 备份执行历史 |

关键约束：

- 同一父目录下活动名称唯一（不区分大小写），由部分唯一索引保证。
- `versions(node_id, version_no)` 唯一。
- 节点删除采用 `deleted_at + delete_batch`，不立即物理删除。
- 审计记录保存当时的显示名称和路径，不依赖后续改名。

## 5. 核心写入规则

### 上传新文件

1. API 先检查权限、名称、父目录、同名冲突和磁盘空间。
2. 请求体流式写入 `tmp/`，同时计算 SHA-256，超过上限立即失败；不把整个文件读入内存。
3. 文件 `fsync` 后移动到 `objects/`，成为不可变对象。
4. 开启 SQLite 事务：
   - 再次检查父目录和同名；
   - 插入 node（先插入，避免版本外键指向不存在的节点）；
   - 插入 object 和 version；
   - 写审计；
   - 提交。
5. 提交失败则对象成为孤儿，由维护任务延迟清理；不会留下指向不存在内容的已提交版本。

### 上传新版本

- 请求必须携带基础的当前版本 ID。
- 在进程内写锁和事务内重新读取节点，若当前版本已改变，返回 `VERSION_CONFLICT`，不静默覆盖。
- 新版本号 = 节点修订号 + 1；更新唯一当前版本指针。

单进程使用互斥锁串行化会改变目录/版本状态的提交操作。SQLite 本身也会串行化写入。

### 历史恢复

- 校验基础版本后，为新版本记录复用原对象（对象不可变），新增版本行并更新当前指针。
- 不删除后来的版本，也不会破坏已有历史。

### 删除与回收站

- 使用递归 CTE 把节点和所有活动子节点标记为同一个删除批次。
- 普通用户不访问回收站；管理员恢复时检查原父目录和名称冲突。
- 永久清理先删除数据库中的版本/节点，再在存储读锁保护下删除无引用对象。文件删除失败会留待 GC，不会破坏数据库一致性。
- 清理单个历史版本时禁止删除当前版本，并检查对象是否仍被其他版本引用。

### 文件系统与数据库一致性

两者不能组成同一个事务，系统选择：

- **允许孤儿对象**，不允许已提交版本引用缺失对象；
- 上传先落盘后提交；
- 清理对象前检查引用；
- 启动/每日维护清理超过 24 小时的临时文件和孤立对象。

## 6. 认证与权限

- 密码：6～128 个字符，Argon2id（64 MB、3 次、2 线程），盐和参数编码在摘要中。
- 会话：32 字节随机令牌，Cookie 仅保存令牌，数据库保存 SHA-256；HttpOnly、SameSite=Lax，HTTPS 下 Secure。
- 登录失败限速：同一用户名 + IP 10 分钟内 5 次失败后锁定 5 分钟。
- 所有修改请求校验 `Origin`/`Sec-Fetch-Site` 同源；静态资源设置 CSP、nosniff、禁止 iframe。
- 角色在服务端每个请求重新从数据库读取，停用账号立即失效。
- 初始化账号带 `is_owner` 标记（唯一），固定为管理员且不能停用；只能由本人维护，其他管理员修改或重置密码会被服务端拒绝。
- 删除账号采用软删除：账号从用户列表移除、不能登录、会话失效，但用户行保留用于历史版本显示上传人；用户名会加后缀释放，可重新创建同名账号。只有主机账号可以删除其他账号。
- 首次初始化只允许回环地址访问，且仅在没有任何用户时可用。

## 7. 备份设计

备份不是复制数据库文件。流程：

1. 获取存储 `RWMutex` 读锁，阻止永久清理删除被备份引用的对象。
2. 使用 `VACUUM INTO` 生成一致的数据库快照。
3. 从快照读取全部版本引用的对象清单。
4. 逐对象复制并计算 SHA-256，复制大小和摘要必须与清单一致。
5. 复制自动生成的根证书和服务器证书（`ca.crt`、`ca.key`、`server.crt`、`server.key`，如存在）。
6. 按快照中的目录树把当前版本复制到 `files/`，生成可直接浏览的可读副本；历史版本仍只保存在 `objects/`。
7. 写入 `manifest.json`、`complete.json` 和可读副本说明。
8. 全部成功才把本次记录标记成功；失败会删除不完整目录并保留上一份成功备份。
9. 按保留份数清理旧的**完整**备份。

恢复命令 `-restore` 只接受带完成标记的备份，校验数据库摘要和每个对象后才复制到空目标目录。

RPO 由备份频率决定（默认 24 小时）；RTO 取决于数据量和介质，应通过演练测量。

## 8. HTTP API 摘要

```text
GET  /api/setup/status
POST /api/setup/admin
POST /api/auth/login | logout | change-password
GET  /api/auth/me

GET  /api/nodes?parent=&q=
GET  /api/folders/tree
GET  /api/nodes/{id} | breadcrumbs | versions | audit | download | download-folder
POST /api/nodes                         新建目录
PATCH /api/nodes/{id}                   改名/移动
DELETE /api/nodes/{id}                  移入回收站
POST /api/nodes/{id}/restore-version
DELETE /api/nodes/{id}/versions/{versionId}

PUT  /api/upload?...                    原始文件流上传
GET  /api/upload/{id}                   幂等状态查询

GET  /api/recycle
POST /api/recycle/{batch}/restore
DELETE /api/recycle/{batch}

GET/POST/PATCH /api/admin/users...
GET  /api/admin/audit | audit.csv
GET/PUT /api/admin/settings
GET  /api/admin/system
GET  /api/admin/backups
POST /api/admin/backups/run
GET  /api/cert | server-cert
```

统一错误格式：

```json
{"error":{"code":"VERSION_CONFLICT","message":"文件已被他人更新，请刷新后重试"}}
```

主要错误码：`INVALID_NAME`、`NAME_EXISTS`、`VERSION_CONFLICT`、`UPLOAD_IN_PROGRESS`、`FILE_TOO_LARGE`、`NO_SPACE`、`PASSWORD_CHANGE_REQUIRED`、`FORBIDDEN`。

## 10. 扩展建议

按需求优先级考虑：

1. 分片上传和断点续传（大文件）。
2. 文件夹上传、整目录 ZIP 下载。
3. 图片/PDF/文本预览。
4. 按共享空间的访问权限（需要扩展 nodes 的命名空间和授权表）。
5. 版本保留策略按数量/容量自动执行（需与备份保护协调）。
6. 文件签出锁，降低“基于旧版本编辑”的冲突概率。

不建议在十几人规模下拆分微服务或引入分布式对象存储；SQLite 单机足够，维护成本更低。

## 11. 已知限制

- 通过 Cookie 的写请求防护依赖同源校验和 SameSite，若将来在前面加反向代理，必须确保 Host/Origin 正确。
- 审计记录不防主机管理员篡改。
- 备份目录如果与数据目录在同一块物理硬盘，无法抵御硬盘损坏。
- 自动备份不补做错过的日期。
- 搜索只匹配名称，最多返回 200 条。
- 自动生成的本地根证书需要客户端手工信任一次，不支持 Firefox 自动配置；主机 IP 变化只会重签服务器证书，根证书不变。
- 文件对象不做去重；空间增长与更新次数成正比。
